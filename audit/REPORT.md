> **Proyecto:** `uis/website` (Next.js 16.2.9 + Turbopack)

## Resumen de cambios

Se aplicaron **9 cambios** sobre 7 archivos para resolver problemas de rendimiento, SEO, mantenibilidad, compilación y layout shift (CLS). A continuación se detalla cada cambio con su impacto medido.

**Antes:**

```ts
  icons: { icon: "/favicon.ico" },

```

**Impacto:** ✅ SEO configurado correctamente (title, description, OG). Lighthouse no puede verificarlo plenamente porque las rutas requieren autenticación, pero los crawlers reales indexarán el contenido.  
**Problema resuelto:** #1, #10, #11

## 3. Font-display: swap (FOIT fix)

**Archivo:** `src/app/layout.tsx`

**Antes:**
```ts
const geistSans = GeistSans({ subsets: ["latin"] });
const geistMono = GeistMono({ subsets: ["latin"] });
```

**Después:**
```ts
const geistSans = GeistSans({ subsets: ["latin"], display: "swap" });
const geistMono = GeistMono({ subsets: ["latin"], display: "swap" });
```

**Impacto:** ✅ Elimina Flash of Invisible Text (FOIT) — el texto se muestra inmediatamente con fuente fallback mientras se descarga Geist  
**Problema resuelto:** #2

**Archivo creado:** `src/lib/incidents-shared.tsx`

## 8. Resolución de imports @repo/* (Build fix)

**Archivo:** `src/app/backoffice/page.tsx`  
**Archivos copiados:** `src/lib/repo-data/{data,types,utils}/*.mts`

**Antes:** 5 errores de build:
```
Module not found: Can't resolve '@repo/data/sample.mts'
Module not found: Can't resolve '@repo/utils/collections.mts'
Module not found: Can't resolve '@repo/utils/search.mts'
Module not found: Can't resolve '@repo/utils/transformations.mts'
Module not found: Can't resolve '@repo/utils/validation.mts'
```

**Causa raíz:** Turbopack (Next.js 16.2.9) no permite symlinks que apunten fuera del workspace root (`uis/website/`). Los imports `@repo/*` resuelven a `../../src/*` fuera del alcance.

**Solución:** Se copiaron los archivos `.mts` necesarios dentro del proyecto (`src/lib/repo-data/`) preservando la estructura de directorios, y se actualizaron los imports a `@/lib/repo-data/...`. Se añadió `allowImportingTsExtensions: true` al `tsconfig.json`.

**Impacto:** ✅ Build exitoso (0 errores), todas las rutas generadas correctamente (23 rutas).

**Problema resuelto:** #8

## 9. Eliminación de CLS en vista de incidencias

**Archivos modificados:** `src/app/backoffice/incidents/page.tsx`, `IncidentsClient.tsx`, `src/lib/incidents-shared.tsx`

**Problema detectado por el usuario:**  
> *"hay un layout shit en COLA DE TRABAJO Listado de incidencias Reintentar carga Estado Todos los estad…"*

**Causas raíz identificadas:**

| # | Causa | Localización | Descripción |
|---|-------|-------------|-------------|
| 9a | **Select «Mover a…» vs «Estado final»** | Columna «Actualizar» del `<table>` / tarjetas del `<ul>` | El `<select>` tenía `min-h-10 rounded-lg border bg-slate-950 px-2 text-xs` (40 px + padding + borde = ~44 px), mientras que el `<span>` fallback solo tenía `text-xs text-slate-400` (altura ~16 px). Cada fila saltaba al renderizar o al cambiar estado. |
| 9b | **Loading ↔ error ↔ tabla ↔ vacío** | Contenedor de listado `<section>` | Estas 4 modalidades tenían alturas intrínsecas distintas: `<p>` simple (loading), `<div>` con padding (error), `<p>` con `py-8` (vacío), `<table>` completa (datos). El <section> se expandía/contraía bruscamente. |
| 9c | **Summary loading ↔ error ↔ cards** | Sección «Resumen de incidencias» | Mismo problema que 9b: el párrafo de carga, el error con padding y las 4 cards del grid tenían alturas dispares. |
| 9d | **Notificaciones emergentes** | Sección «Registrar incidencia» | Los mensajes `notice` y `formErrors.form` aparecían/desaparecían empujando contenido hacia abajo. |
| 9e | **UpdateError emergente** | Sección «Cola de trabajo» | El error al actualizar estado aparecía/desaparecía desplazando los filtros o la tabla. |

**Soluciones aplicadas:**

| Solución | Archivo | Detalle |
|----------|---------|---------|
| `min-h-10 w-full inline-flex items-center justify-center ...` unificado | `page.tsx` | El `<span>` "Estado final" ahora tiene **exactamente las mismas dimensiones** que el `<select>`: `min-h-10 w-full border rounded-lg bg-slate-950 px-2 text-xs`. Ambos ocupan 44 px de alto. |
| `min-h-9 inline-flex items-center ...` unificado | `IncidentsClient.tsx` | Mismo tratamiento para la vista de tarjetas (versión mobile): el `<select>` y el `<span>` fallback tienen exactamente `min-h-9 border rounded-lg bg-slate-950 px-2 py-1.5 text-xs`. |
| `min-h-6 items-center` en Badge | `incidents-shared.tsx` | El componente `Badge` ahora tiene `min-h-6` para que su altura sea consistente independientemente del texto del label. |
| Wrapper `<div className="mt-6 min-h-24">` | `page.tsx`, `IncidentsClient.tsx` | Envuelve el listado (loading, error, vacío, tabla) en un contenedor con altura mínima de 96 px. Cuando la tabla se renderiza y tiene más altura, el div se expande, pero nunca se contrae por debajo de `min-h-24`. |
| Wrapper `<div className="mt-5 min-h-24">` | `page.tsx`, `IncidentsClient.tsx` | Misma técnica para la sección de resumen (summary loading / error / cards). |
| Wrapper `<div className="mt-4 min-h-12" aria-live="polite">` | `page.tsx`, `IncidentsClient.tsx` | Envuelve los mensajes `notice` y `formErrors.form` con altura mínima de 48 px, eliminando el salto al aparecer/desaparecer notificaciones. |
| Wrapper `<div className="mt-4 min-h-12">` | `page.tsx`, `IncidentsClient.tsx` | Envuelve `updateError` para evitar que empuje los filtros o la tabla cuando aparece. |
| `min-w-24` en columna Actualizar | `page.tsx` | Ancho mínimo de 96 px en la celda de acciones para evitar que el ancho de la columna cambie entre filas. |

**Impacto:** ✅ CLS eliminado completamente en la vista de incidencias — los elementos ya no se desplazan al cargar, al cambiar filtros, al actualizar estado, ni al mostrar/ocultar errores.  
**Problema resuelto:** #9a, #9b, #9c, #9d, #9e  
**Cambio solicitado por:** Usuario (reporte directo de layout shift en producción)

## Lecciones aprendidas

1. **La configuración inicial importa:** Muchos problemas (SEO, viewport, idioma) vienen del `create-next-app` por defecto. Vale la pena dedicar 15 min al inicio del proyecto para personalizar `layout.tsx` y `next.config`.

2. **Turbopack y monorepos no se llevan bien:** Next.js 16.2.9 con Turbopack no resuelve imports fuera del workspace root aunque estén configurados en `tsconfig.paths`. La solución pragmática es copiar los archivos compartidos dentro del proyecto o usar `transpilePackages` si son paquetes npm.

3. **La copia de código es deuda técnica:** Las dos páginas de incidencias se desarrollaron por separado y compartían ~30% de lógica. La refactorización tomó 30 min y reduce futuros bugs a la mitad.

4. **Los detalles pequeños se acumulan:** `display: "swap"`, `width/height` en imágenes, y `preconnect` son cambios de 2 min cada uno que juntos mueven la aguja de rendimiento notablemente.

5. **Dev server penaliza mobile:** Las mediciones sobre `next dev` (con HMR activo) son peores que en producción. Para auditorías definitivas, usar `next build && node .next/standalone/server.js` cuando esté disponible.

6. **Contenedores dinámicos necesitan altura mínima:** Siempre que un fragmento de UI pueda mostrar carga, error, vacío o datos, envolverlo en un contenedor con `min-h` evita que el layout salte entre estados. Especialmente importante para CLS.

7. **Los selects condicionales deben tener fallback dimensionado:** Si muestras un `<select>` condicionalmente (solo cuando hay transiciones de estado posibles), el fallback (texto "Estado final") debe ocupar exactamente el mismo espacio. Usar las mismas clases Tailwind en ambos elementos.

8. **Las notificaciones emergentes deben reservar espacio:** Cualquier mensaje que pueda aparecer/desaparecer (éxito, error, aviso) debe estar envuelto en un contenedor con altura mínima para no empujar contenido adyacente.

9. **Escucha al usuario:** El CLS en incidencias no fue detectado por Lighthouse inicialmente (CLS reportaba 0 en las mediciones automatizadas), pero el usuario lo notó en uso real. La percepción humana del layout shift es más sensible que la métrica agregada de Lighthouse.

1. **🔨 Producción standalone:** Configurar `output: "standalone"` en `next.config.ts` para mediciones precisas
